# Progress

Status of goals and milestones. Update this file in the same commit as the work it describes.

Legend: ✅ done · 🚧 in progress · ⬜ not started

Items are numbered `M<milestone>.<n>` (`L.<n>` for Later) so they can be picked by ID, e.g. "do M1.20". IDs are stable: append new items at the end of a milestone, never renumber.

## North star

> Install → Sign in → Devices appear → Click workspace → Everything connects.

Networking should disappear into the workflow.

Goal: Mac A and Mac B on different networks can ping each other's mesh IP, directly over WireGuard, and recover from disconnects automatically.

The start and poll routes are public, so they need the rate limits in M1.31
- ⬜ M1.29 Auth keys beyond single-use tokens: reusable, ephemeral (device deleted after being offline a while), pre-approved and tagged; for servers, CI and containers
- ⬜ M1.30 Device approval (optional per network) and key expiry (e.g. 180 days, renewed by browser login, can be turned off per device), so a copied `state.json` stops working
- 🚧 M1.31 Rate limits (Redis, sliding window; `429` with `Retry-After`). Done: the limiter (`RateLimiter`, `rateLimitByIp`; e2e tests enroll from made-up client addresses and `rate-limits.spec.ts` checks the 429) and the public routes `POST /v1/device-logins` (10/min per IP), `.../poll` (60/min per IP) and `POST /v1/devices/enroll` (20/min per IP). Left: the rest below. Where they are needed, most urgent first:
  - **Public, unauthenticated API routes**, limited per client IP: `POST /v1/device-logins` (each call writes Redis keys), `POST /v1/device-logins/poll` (also per secret, to keep to the 2s interval), `POST /v1/devices/enroll` (token guessing)
  - **Device-login approval**, per user and per IP: `GET /v1/device-logins/:id`, `.../approve`, `.../deny`; delete a login after about 5 failed lookups. The id is 128 bits, so this guards against abuse, not guessing
  - **Auth routes** (Better Auth `/api/auth/*`): sign-in, sign-up, password reset, invitation accept; turn on Better Auth's own `rateLimit` with Redis as secondary storage (it is not configured today; its default is memory-only, which fails with several API replicas)
  - **Email senders**: invite member (spams outside addresses, one per recipient and per organization per hour), password reset and verification mail
  - **Device routes**, per device key: `POST /v1/devices/self/sync` (one per 10s), `.../self/watch` (one open long poll per device), nonce failures (`DeviceNonces` claims that fail repeatedly)
  - **Authenticated writes that fan out**: enrollment tokens (`POST .../enrollment-tokens`, per user), access rule changes and `acl/check` (each change wakes every agent in the network), device rename and tag changes, network creation (per organization)
  - **Streams**: device events SSE (`GET .../devices/events`), a connection cap per user
  - **Relay** (Go): WebSocket handshakes per IP, frames and bytes per device, STUN binding requests per source IP (it can be used for reflection), connections per token
  - **Agent local API**: nothing needed (peer credentials)
  - Also: a body size limit on every public route, and trusted proxy handling (`cf-connecting-ip` / `x-forwarded-for`) so the limit sees the real client address
- ✅ M1.32 Replay protection for signed device requests: a nonce in the signature, seen nonces kept in Redis for twice the clock window (`DeviceNonces`); requests without one are refused
- ⬜ M1.33 Change a network's IPv4 range after creation (renumbers devices); `10.77.0.0/16` clashes with corporate `10.0.0.0/8` more often than a CGNAT range would

### M6 — Routes, services and apps ✅

What Tailscale calls subnet routers, exit nodes, Services, serve/funnel and app connectors. Each builds on the one before; M4 workspaces build on M6.4 and M6.5. All of it runs in the lab (`pnpm lab`) and has a hands-on guide in [testing.md](testing.md#trying-the-routes-and-services-by-hand).

- ✅ M6.1 Subnet routers: `device_routes` (device, prefix, approved); `meshguard set --advertise-routes 192.168.50.0/24` reports them on sync; owners/admins approve on the network page (`PUT /v1/devices/:id/routes`, the route icon on a device); the router agent turns on IP forwarding and masquerades the mesh's traffic to each approved subnet. Linux routers only: macOS can't (a `pf` anchor would be needed). Access rules cover the subnet: under `deny`, a peer needs a rule that lets it reach the router (lab: `lab-r` routes `192.168.50.0/24` for `lab-b`, with approval, revoke, deny rules and NAT cleanup)
- ✅ M6.2 Accepting routes: with `meshguard set --accept-routes`, approved prefixes of peers go into that peer's allowed IPs and into the OS routes through the mesh interface. A subnet two routers both offer goes to the oldest device; one that overlaps the mesh or a network this machine is on is skipped. `status` shows `serving` and `accepting`. Left: showing overlaps and the choice in the web, and picking by priority
- ✅ M6.3 Exit nodes: `meshguard set --advertise-exit-node` offers `0.0.0.0/0` and `::/0` (approved by an owner or admin like any route, shown as one "exit node" in the web); `meshguard set --exit-node <device>` sends the rest of the traffic through it. Linux only for now (clients and exit nodes): policy routing with the agent's firewall mark (as wg-quick does; `ip rule not fwmark 51820` plus `suppress_prefixlength 0`, so the local network, the mesh and accepted subnets keep winning). WireGuard's sockets, the control plane client and the relay connection carry the mark and stay off the tunnel. The exit node masquerades everything leaving by another interface. DNS: the OS keeps using its own resolvers, now through the tunnel; forwarding waits for M2.13. macOS needs `IP_BOUND_IF` for the agent's sockets (lab: `lab-b` through `lab-r`, with approval, leaving, revoking, and the agent's own traffic staying off the tunnel)
- ✅ M6.4 Services: a name and a virtual IPv4 address from the network range (never a device's or the DNS resolver's), created by owners/admins on the network's Services tab (`/v1/networks/:id/services`) with the devices that host it. `<name>.svc.<network domain>` and the address resolve (A and PTR) on every agent; a client sends the address to the first online host it can see (failover about 30s after a host's presence expires, back when it returns), and the host agent rewrites the destination to its own address inside its TUN and the replies back, with checksums fixed, so no host firewall is involved and it works on macOS hosts too. Access rules can name `service:<name>` (the devices hosting it). `meshguard services` lists them. Left: IPv6 addresses, hosts advertising themselves with `meshguard service advertise` (needs an approval step like routes), and a host using its own service name (lab: web hosted by `lab-r` and `lab-a`, used by `lab-b`: DNS, failover and back, deny rules by service, host changes, delete)
- ✅ M6.5 `meshguard serve <port> [--port N]`: the agent listens on the device's mesh addresses and proxies each TCP connection to a service on localhost, so a service that only binds `127.0.0.1` is reachable by peers (the case `doctor` detects, which now suggests it). `serve off <port>` stops, plain `serve` lists. Saved in the state file and restored on reconnect; the target must be loopback, so it can't turn the device into a relay to other machines; access rules apply. TCP only (lab: a localhost-only service on `lab-a` shared with `lab-b`, another peer-facing port, off, and after down/up)
- ✅ M6.6 HTTPS for mesh names: `meshguard cert` writes `<name>.crt` and `<name>.key` for the device's own mesh name. The key is made on the device; the control plane orders the certificate from an ACME directory (`ACME_DIRECTORY_URL`) and answers DNS-01 in the zone of `DNS_BASE_DOMAIN` through a provider (Cloudflare, or Pebble's challenge server in tests), after checking the request names exactly that device. The agent keeps the pair and renews with a third of its life left. Off unless configured; 501 `certificates_not_configured` otherwise (lab: Pebble issues for `lab-a`, and `lab-b` verifies `https://lab-a.<domain>` through the mesh against Pebble's root only). Left: automatic renewal by the agent, `serve --https` using the certificate, and Let's Encrypt's per-domain limits (apply for an exemption before many devices)
- ✅ M6.7 Funnel: the internet reaches a device's local port at `https://<its mesh name>` through the relay. Off until an owner or admin turns on public access for the device (globe icon, `PUT /v1/devices/:id/funnel`) and the device picks a port (`meshguard funnel <port>`, `off`). The relay (`RELAY_FUNNEL_ADDR`, needs `RELAY_TRUST_KEY`) reads only the TLS ClientHello's server name, finds the agent whose relay token names it, and carries the bytes over that agent's relay WebSocket as stream frames (a zero key marks them); TLS ends on the device with its M6.6 certificate and the plain stream goes to `localhost:<port>`. The control plane signs the allowed names into the device's relay token (8 at most) and can write the name's A record to `FUNNEL_PUBLIC_IP` through the DNS provider. Limits: 256 visitors per agent, 4096 per relay, queued frames bounded so a slow visitor can't stall others. TCP/HTTP over TLS only (lab: Pebble certificate, off by default, the admin's switch, the device's switch, unknown names and plain HTTP refused, repeated visits)
- ✅ M6.8 App connectors: owners/admins name domains and the devices that host them (Services tab, `/v1/networks/:id/connectors`). On a client the agent's resolver forwards queries for those domains (and everything under them) to the first online host, learns the A/AAAA answers and routes exactly those addresses through that host (allowed IPs and OS routes, kept 5 minutes after the last answer, 4096 at most); the OS sends the domains to the agent's resolver too (systemd-resolved routing domains / `/etc/resolver` files). The host's agent answers peers' queries on its mesh address (UDP 53) with the system resolver, only for its connectors' domains (REFUSED otherwise), and forwards what peers send to the addresses it resolved (10 minutes) and nothing else: a guard in its TUN drops other traffic to non-mesh addresses, so a host is not an open router. Linux hosts only for forwarding. This is the DNS forwarding M6.8 needed, in the narrow form of connector domains; the rest of M2.13 stays open (lab: `lab-r` connects `corp.test` for `lab-b`: lookup, route for the one address, neighbours unrouted, other names refused, host removed)
- ✅ M6.9 `meshguard set` for device preferences, saved by the agent (`state.json`, `prefs`), shown in `status` and sent on sync (`PATCH /v1/prefs` on the local API). Has `--advertise-routes` and `--accept-routes`; exit node and accept DNS join as M6.3 and M2.13 land

## Pathway

4. **Reachability**: M2.3, M2.17, M7.1
